# 提示词工程指南 — AI Career Companion

## 一、什么是提示词工程

提示词工程（Prompt Engineering）是系统性地设计和迭代 LLM 系统提示词（System Prompt）的过程，目标是**精确控制 Agent 的行为边界**——告诉它：

- **角色是什么**（身份、语气、风格）
- **能做什么**（能力范围、可用工具）
- **不能做什么**（安全边界、拒绝策略）
- **怎么做决策**（路由规则、优先级、工具选择策略）
- **输出什么格式**（结构化要求、长度限制）

在 Agent 架构中，系统提示词的位置：

```
用户输入 → [System Prompt + Memory + Tool Schema + User Message] → LLM API → Agent 响应
                ↑
         提示词工程的作用点
```

## 二、项目中的两套提示词方案

本项目包含两套独立的提示词架构，分别在 `demo/` 和 `demo_new/` 下。

### 2.1 demo/ — 模板化 + 三层分离

**目录结构**：

```
demo/opencareer/
├── prompts/
│   ├── __init__.py          ← PromptRegistry: YAML 加载 + 点号访问 + Template 替换
│   ├── brain_system.yaml    ← BrainAgent 路由规则
│   ├── work_system.yaml     ← WorkAgent 职业建议逻辑
│   └── system_prompts.yaml  ← 公共提示词片段
├── personas/
│   └── default.yaml         ← 人设: name / tone / style / values
└── agents/
    └── base_agent.py        ← _build_system_prompt(): 组装最终提示词
```

**三层分离设计**：

```
第1层 - 人设层 (personas/default.yaml)
  → 定义 Agent "是谁"
  → 字段: name, tone, style, core_values
  → 示例: "你是一个温暖专业的职业规划顾问"

第2层 - 任务层 (prompts/*.yaml)
  → 定义 Agent "做什么"
  → 内容: 路由规则、回答边界、流程步骤、决策逻辑
  → 示例: "当用户情绪低落时，优先共情再给建议"

第3层 - 工具层 (MCP tool schema / Skill.description)
  → 定义 Agent "能用什么"
  → 自动生成: langchain-mcp-adapters 将 tool name + description + input_schema 注入 LLM 上下文
  → 无需手动维护
```

**组装流程**（`BaseAgent._build_system_prompt()`）：

```
personas/default.yaml ────┐
                          ├──→ string.Template 变量替换 ──→ 最终 System Prompt
prompts/xxx_system.yaml ──┘
                          ↓
              $persona_name, $tone, $style 等占位符被填充
                          +
        ConversationContext (mood, history, user_profile) 动态注入
```

**关键机制**：

| 机制 | 实现方式 | 用途 |
|------|---------|------|
| 模板加载 | `PromptRegistry` 启动时加载全部 YAML | 集中管理，支持点号路径访问 |
| 变量替换 | `string.Template` | `$persona_name` 等占位符 → 实际值 |
| 动态注入 | `ConversationContext` | 当前情绪、历史摘要、用户画像 |
| 关注点分离 | 人设/任务/工具 三个独立层级 | 改人设不改任务，改任务不改工具 |

---

### 2.2 demo_new/ — 硬编码 + MCP 模板分离

**目录结构**：

```
demo_new/opencareer/
├── agents/
│   └── career_agent.py     ← 系统提示词硬编码在 Python 字符串中
└── mcp/
    └── prompts/
        ├── __init__.py           ← YAML 加载器 + SkillRegistry
        ├── emotion_support.yaml  ← 按关键词匹配的情绪回复模板
        ├── career_advice.yaml    ← 按话题匹配的职业建议
        ├── interview_prep.yaml   ← 面试题库 + STAR 提示
        └── skills.yaml           ← 技能定义 (name/description/params/steps)
```

**架构特点**：

- 系统提示词是 `career_agent.py` 中的一个**硬编码字符串**，修改需要改代码
- MCP 侧的 YAML 模板**不参与 Agent 系统提示词的构造**
- MCP YAML 只被 Server 端的关键词匹配逻辑使用（无 LLM 参与）
- 工具描述由 `langchain-mcp-adapters` 自动从 MCP tool schema 生成

---

### 2.3 两种方案对比

| 维度 | demo/ | demo_new/ |
|------|-------|-----------|
| 提示词管理 | YAML 模板 + Template 变量 | 硬编码字符串 |
| 人设系统 | 独立 `personas/default.yaml` | 无 |
| 动态上下文注入 | mood / history / user_profile | 无 |
| 工具描述 | Skill 类内定义 | 自动从 MCP tool schema 生成 |
| 提示词迭代方式 | 改 YAML 文件，重启即可 | 改 Python 代码再重启 |
| 关注点分离 | 人设 / 任务 / 工具三层 | 全部混在代码里 |
| 多 Agent 支持 | 每 Agent 独立提示词 | 单 Agent |

## 三、提示词工程的核心原理

### 3.1 上下文窗口分配

LLM 的上下文窗口是有限资源，所有内容都要竞争：

```
[System Prompt] + [Memory/History] + [Tool Schema] + [Tool Results] + [User Input] ≤ Context Window
```

提示词工程需要在**指令完整度**和**空间占用**之间权衡：

- 系统提示词越长 → 留给对话历史和工具返回结果的空间越少
- 系统提示词越短 → Agent 行为可能不够受控

项目的 `ConversationContext`（demo/）和 `long_term_memory`（demo_new/）通过截断历史来管理这个矛盾。

### 3.2 分层设计

将提示词按关注点拆分，各自独立维护：

```
第1层: 人设层 → 改语气不改行为
第2层: 任务层 → 改规则不改人设
第3层: 工具层 → 改工具不碰前两层
```

好处：迭代成本低、回滚容易、A/B 测试只需替换单层。

### 3.3 变量系统

用占位符而非硬编码值，让同一套提示词适配不同人设/场景：

```yaml
# YAML 模板中
greeting: "你好，我是$persona_name，我的风格是$tone"

# 运行时替换为
greeting: "你好，我是小助手，我的风格是温暖专业的"
```

### 3.4 指令优先级

LLM 对指令的理解存在优先级规则：

1. **系统提示词中的强约束 > 弱建议**
2. **否定指令 > 肯定指令**（"不要做X" 优先级高于 "可以做Y"）
3. **靠后的指令 > 靠前的指令**（在长上下文中，末尾指令权重更高）
4. **工具描述中的约束 > 系统提示词中的泛泛而谈**

实际应用：
- 安全边界用否定指令（"绝对不要编造信息"）
- 工具使用规则放在工具描述里更有效
- 关键约束放在系统提示词末尾

### 3.5 Few-shot vs Zero-shot

```
Zero-shot:   只给规则，不给示例
             示例: "回答要简洁，不超过200字"

Few-shot:    给具体示例让模型模仿
             示例: "Q: 我适合什么职业？
                    A: 基于你的背景，推荐以下3个方向：1. ..."
```

项目当前主要是 **Zero-shot + 工具描述**，在 MCP 工具层面有一些类似 Few-shot 的模板（如 `career_advice.yaml` 中的话题-建议映射）。

## 四、提示词工程操作指南

### 4.1 文件和对应关系

| 你想调整的内容 | 修改的文件 | 需不需要改代码 |
|---------------|-----------|--------------|
| Agent 的语气/性格 | `demo/opencareer/personas/default.yaml` | 否 |
| BrainAgent 路由规则 | `demo/opencareer/prompts/brain_system.yaml` | 否 |
| WorkAgent 回答策略 | `demo/opencareer/prompts/work_system.yaml` | 否 |
| 公共提示词片段 | `demo/opencareer/prompts/system_prompts.yaml` | 否 |
| MCP 工具的回复模板 | `demo_new/opencareer/mcp/prompts/*.yaml` | 否 |
| demo_new Agent 系统提示词 | `demo_new/opencareer/agents/career_agent.py` | 是 |

### 4.2 迭代流程

```
1. 定位目标层
   → 判断改动属于人设/任务/工具哪一层

2. 修改 YAML 文件
   → 只改对应层的文件，不跨层修改

3. 重启服务
   → demo/ 重启 FastAPI (python -m opencareer.api.web_api)
   → demo_new/ 重启 MCP server + CareerAgent

4. 固定测试用例验证
   → 用相同的用户输入，对比修改前后的 Agent 输出
   → 关注: 是否达到预期行为？是否引入副作用？

5. 保留有效调整，回滚无效调整
   → Git 跟踪每次修改，方便回溯
```

### 4.3 调试技巧

**1. 打印最终 System Prompt**

在 `BaseAgent._build_system_prompt()` 末尾加 log：
```python
logger.debug(f"Final system prompt:\n{system_prompt}")
```
确认变量替换和动态注入的结果是否符合预期。

**2. 隔离测试**

测试单一修改时，保持其他变量不变：
- 同一个用户输入
- 同一段对话历史
- 只改了目标 YAML 中的一个字段

**3. 关注 Token 消耗**

系统提示词的 token 数会直接影响每次 API 调用的成本和延迟。如果提示词过长，优先精简工具描述和示例。

### 4.4 常见问题

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| Agent 忽略指令 | 指令位置太靠前，被后续信息稀释 | 把关键约束移到系统提示词末尾 |
| Agent 不调用工具 | 工具描述不清晰，或系统提示词没强调工具使用 | 优化 MCP tool 的 description，在任务层增加工具使用规则 |
| Agent 回答千篇一律 | 人设层占比过大，压制了任务层 | 精简人设描述，增加任务层的行为多样性指令 |
| 输出过长/过短 | 缺少长度约束 | 在任务层增加具体的字数/格式要求 |
| Agent 越权回答 | 安全边界描述太弱 | 用否定指令 + 具体示例："如果你无法确定答案，直接说'我不确定'，不要编造" |

## 五、进阶方向（当前项目可扩展）

下列能力在当前项目中已有基础但尚未工程化：

### 5.1 动态提示词选择

根据用户意图自动切换不同的系统提示词模板：

```
用户: "我面试很紧张" → 加载 emotion_support 提示词
用户: "怎么改简历"   → 加载 career_advice 提示词
```

当前 demo/ 的 BrainAgent 已实现意图路由（决定交给哪个 Agent），每个 Agent 有独立的 YAML 文件，架构上已支持此模式。

### 5.2 Few-shot 示例注入

在提示词中加入成功案例的示例：

```yaml
examples:
  - input: "我适合转行做AI吗"
    output: "让我先了解你的背景：1. 当前岗位 2. 技术栈 3. 兴趣方向"
```

当前 `career_advice.yaml` 和 `emotion_support.yaml` 已有模板式回复，可以扩展为 Few-shot 格式注入系统提示词。

### 5.3 A/B 测试框架

同时维护两套提示词，通过配置切换：

```python
# settings 中增加
PROMPT_VERSION = "v1"  # 或 "v2"
```

用相同的用户输入对比输出质量，数据驱动提示词优化。

### 5.4 提示词版本管理

将每次 YAML 修改作为一个版本记录：

```
prompts/
├── brain_system.yaml       ← 当前版本
└── versions/
    ├── brain_system_v1.yaml
    ├── brain_system_v2.yaml
    └── brain_system_v3.yaml
```

## 六、总结

| 层次 | demo/ 文件 | 作用 | 迭代方式 |
|------|-----------|------|---------|
| 人设 | `personas/default.yaml` | 身份、语气、风格 | 修改 YAML |
| 任务 | `prompts/brain_system.yaml`, `work_system.yaml` | 路由规则、回答策略 | 修改 YAML |
| 公共 | `prompts/system_prompts.yaml` | 跨 Agent 共享片段 | 修改 YAML |
| 工具 | MCP tool schema | 工具名称、描述、参数 | 修改 Skill 类 / MCP 装饰器 |
| 动态 | `ConversationContext` | 情绪、历史、画像 | 由 Agent 运行时注入 |
