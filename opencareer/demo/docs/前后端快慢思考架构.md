# 前后端快慢思考架构（Actor-Director Pattern）

## 一、核心思想

### 1.1 问题背景

当前架构中，用户发消息 → 后端 LLM 深度思考 → 生成完整回答 → 前端一次性渲染。存在两个体验问题：

1. **等待时间过长**：DeepSeek API 深度需求分析 + 下游智能体生成回答，数秒到数十秒的空白等待
2. **替换式修正很机械**：后端生成完整回答后替换前端占位内容，用户能感知到"被替换"，不像真人聊天

### 1.2 设计理念：演员-导演模式

仿照人类微信聊天行为——**一长段话拆成多个气泡发送，边说边想，想好了再补充/纠正**。

```
┌─────────────────────────────────────────────────────────┐
│                     Actor-Director 架构                    │
│                                                         │
│  前端 (Actor / 演员)          后端 (Director / 导演)       │
│  ┌─────────────────┐        ┌─────────────────────┐     │
│  │ 快思考 (System 1)│        │ 慢思考 (System 2)    │     │
│  │ 直觉、模式匹配    │        │ 深度推理、策略规划    │     │
│  │                 │        │                     │     │
│  │ • 意图识别       │        │ • 需求深度分析       │     │
│  │ • 气泡生成       │  WS    │ • 行为序列规划       │     │
│  │ • 打字模拟       │◄──────►│ • 前端行为监控       │     │
│  │ • 话题接续       │        │ • 纠正与干预         │     │
│  └─────────────────┘        └─────────────────────┘     │
│                                                         │
│  类比：演员在台上即兴表演，导演在后台把控方向                   │
│  演员不需要等导演完整剧本，先开口，导演随时递纸条调整              │
└─────────────────────────────────────────────────────────┘
```

### 1.3 认知科学基础：Kahneman 双系统理论

| | System 1 (快思考) | System 2 (慢思考) |
|---|---|---|
| **位置** | 前端 | 后端 |
| **特点** | 直觉、自动、快速 | 理性、刻意、缓慢 |
| **延迟** | < 500ms | 2-15s |
| **能力** | 模式匹配、模板填充 | 深度推理、策略规划 |
| **产出** | 聊天气泡序列 | 行为计划 + 纠正指令 |

### 2.2 角色职责

#### 前端 Actor（演员）

| 职责 | 说明 |
|---|---|
| **意图识别** | 基于关键词 + 规则的快速意图分类（job/emotion/mixed/clarify） |
| **气泡生成** | 根据意图匹配行为模板，生成 2-5 个气泡的序列 |
| **打字模拟** | 逐字/逐词渲染，随机 typing 延迟，模拟真人输入节奏 |
| **话题接续** | 在等待后端策略期间，维持对话流不中断 |
| **策略执行** | 接收后端下发的 Strategy，调整/追加/替换气泡 |

#### 后端 Director（导演）

| 职责 | 说明 |
|---|---|
| **深度分析** | LLM 驱动的需求分析 + 情绪评估 + 上下文理解 |
| **策略规划** | 将分析结果转化为行为序列（Action Plan），而非回答文本 |
| **行为监控** | 接收前端行为报告，判断是否偏离正确方向 |
| **纠正干预** | 前端跑偏时下发 Correction，以自然"改口"形式修正 |
| **长期记忆** | 维护 ConversationContext，累积情绪状态，识别模式 |

## 三、前端快思考：BubbleEngine

### 3.1 架构设计

```
BubbleEngine
├── IntentClassifier     # 意图分类器（关键词 + 规则）
├── BehaviorMapper       # 行为映射器（意图 → 行为模板）
├── BubbleGenerator      # 气泡生成器（模板填充 → 气泡序列）
├── BubbleQueue           # 气泡队列（sent / queued / planned）
├── TypingSimulator       # 打字模拟器（延迟、逐字输出）
└── StrategyExecutor     # 策略执行器（接收后端指令）
```

### 3.2 意图分类器（IntentClassifier）

基于现有 `brain_agent.py` 中 `_simulate_demand_analysis()` 的关键词匹配逻辑，将其移植到前端：

```typescript
// IntentClassifier 核心逻辑
const JOB_KEYWORDS = [
  "面试", "简历", "学习", "技能", "职业", "求职",
  "offer", "薪资", "转行", "跳槽", "实习", "工作"
]

const EMOTION_KEYWORDS = [
  "紧张", "焦虑", "害怕", "迷茫", "压力", "失落",
  "没有信心", "担心", "崩溃", "难过", "烦躁"
]

function classifyIntent(input: string): Intent {
  const jobCount = countMatches(input, JOB_KEYWORDS)
  const emotionCount = countMatches(input, EMOTION_KEYWORDS)

  if (emotionCount >= 3 || hasCrisisSignal(input)) return "emotion_first"
  if (jobCount > 0 && emotionCount > 0) return "mixed"
  if (jobCount > 0) return "job_related"
  if (emotionCount > 0) return "emotional_support"
  return "clarify"
}

function hasCrisisSignal(input: string): boolean {
  const crisisKeywords = ["不想活了", "绝望", "崩溃了", "撑不下去"]
  return crisisKeywords.some(k => input.includes(k))
}
```

**要点**：
- 分类逻辑与后端 `_simulate_demand_analysis()` 保持一致，但不调用 LLM
- 分类结果在 5ms 内返回，不阻塞气泡生成
- 危机信号优先检测（安全第一）

```typescript
      { type: "validate", templates: ["{keyword}是很正常的，很多人都经历过"] },
      { type: "support", templates: ["别担心，我们一起来想办法"] },

  },
  // ... 更多模板
}
```

### 3.4 气泡队列（BubbleQueue）

气泡分为三类，按优先级和可修改性区分：

```
┌────────────────────────────────────────────┐
│              气泡队列状态模型                │
│                                            │
│  [sent]       已发送    ■ 不可撤销           │
│                         ■ 已被用户看到        │
│                         ■ 只能追加"改口"纠正   │
│                                            │
│  [queued]     排队中     ■ 可替换/删除        │
│                         ■ 尚未发送给用户      │
│                         ■ 后端策略可修改       │
│                                            │
│  [planned]    计划中     ■ 后端驱动生成        │
│                         ■ StrategyPlanner    │
│                         指定内容和时机         │
└────────────────────────────────────────────┘
```

```typescript
interface Bubble {
  id: string
  type: "sent" | "queued" | "planned"
  content: string
  fragmentIndex: number  // 属于第几个 conversation fragment
  isCorrectable: boolean // 是否可以被纠正（sent=true, 通过改口）
  plannedDelay?: number   // planned 气泡的发送延迟(ms)
}
```

### 3.5 打字模拟器（TypingSimulator）

模拟微信打字体验的核心模块：

```typescript
interface TypingConfig {
  charsPerTick: number       // 每次吐出字数 (1-3)
  tickInterval: number       // 基础间隔(ms) (80-200)
  variability: number        // 随机波动 (0.3 = ±30%)
  pausePunctuation: number   // 标点符号处额外停顿(ms) (300-800)
  longMessageThreshold: number // 超过此长度拆分气泡 (40字)
}

const DEFAULT_TYPING_CONFIG: TypingConfig = {
  charsPerTick: 2,
  tickInterval: 120,
  variability: 0.3,
  pausePunctuation: 500,
  longMessageThreshold: 40,
}
```

**关键行为**：
- 超过 `longMessageThreshold` 的文字自动拆分为新气泡
- 标点符号处增加停顿，模拟真人思考
- 气泡间间隔 800-2000ms，模拟阅读+打字时间


## 四、后端慢思考：StrategyPlanner

### 4.1 核心转变：从生成回答到生成策略

```
旧模式（Answer Generator）：
  用户输入 → DeepSeek API → 完整回答文本 → 前端渲染

新模式（Strategy Planner）：
  用户输入 → DeepSeek API → 行为序列 + 约束条件 → 前端执行
```

后端不再输出回答文本，而是输出**行动计划**：

```json
{
  "type": "strategy",
  "version": 1,
  "timestamp": 1715432000,
  "demand_analysis": {
    "demand_type": "mixed",
    "job_aspect": "面试准备",
    "emotion_primary": "anxiety",
    "support_intensity": "medium",
    "confidence": 0.92
  },
  "action_plan": {
    "current_turn": {
      "validate": ["acknowledge_job", "acknowledge_emotion"],
      "correct": null,
      "append_bubbles": [
        {
          "type": "planned",
          "content": "我看了你的简历，明天的面试是技术岗，我们可以重点准备算法和项目经验",
          "delay_ms": 3000
        }
      ]
    },
    "next_turns": [
      {
        "trigger": "user_provides_job_detail",
        "actions": ["explore_resume_match", "suggest_mock_interview"]
      },
      {
        "trigger": "emotion_escalates",
        "actions": ["pause_work", "full_emotional_support"]
      }
    ]
  },
  "constraints": {
    "tone": "warm_professional",
    "max_bubbles_per_burst": 4,
    "avoid_topics": ["薪资谈判"],
    "persona_guidance": "既是职业顾问又是支持性朋友"
  },
  "correction_preplan": {
    "if_frontend_overpromises": "用'让我再确认一下'引入修正",
    "if_frontend_misses_emotion": "用'而且我注意到你好像...'补充情绪关注"
  }
}
```

### 4.2 策略生成流程

```
用户输入 ──→ DemandAnalyzer ──→ EmotionAssessor ──→ ContextIntegrator
                                        │
                                        ▼
                               StrategyGenerator
                                        │
                          ┌─────────────┼─────────────┐
                          ▼             ▼             ▼
                    ActionPlan    Constraints    CorrectionPreplan
                          │             │             │
                          └─────────────┼─────────────┘
                                        ▼
                               Strategy JSON
                                        │
                                        ▼
                              WebSocket → 前端
```

**DemandAnalyzer**：复用现有 `_analyze_demand()` 的 LLM 调用，输出结构化需求分析
**EmotionAssessor**：复用 `get_accumulated_emotion_assessment()`，考虑历史累积情绪
**StrategyGenerator**：新增模块，将分析结果转换为行为计划
**CorrectionPreplan**：预判前端可能出错的方向，提前准备纠正话术

### 4.3 情绪累积评估

复用 `ConversationContext`（`conversation_context.py:309-329`）中已有的能力：

```python
def get_accumulated_emotion_assessment(self) -> dict:
    """
    返回：
    - negative_ratio: 最近N轮中负面情绪占比
    - consecutive_negative: 连续负面轮数
    - should_defer_work: 是否应暂停工作话题
    """
```

这是后端 Director 判断"是否需要介入"的关键输入：
- `consecutive_negative >= 3`：强制介入，前端的安抚模板可能不够
- `should_defer_work == true`：发送 constraint `{ "avoid_topics": ["工作", "面试"] }`

### 4.4 Monitor 监控器

```
Monitor 工作流：
  1. 接收前端报告（每发送一个气泡，前端上报气泡内容）
  2. 对比当前 Strategy 中的预期行为
  3. 判断偏差等级：
     - GREEN: 前端行为在预期范围内，不干预
     - YELLOW: 轻微偏差，发送软纠正（追加气泡引导）
     - RED: 严重偏差，发送硬纠正（改口 + 话题重置）
  4. 下发 Correction 指令
```

### 5.2 新增消息类型

为支持 Actor-Director 架构，新增以下消息类型：

```typescript
// === 新增消息类型 ===

// 1. 策略下发（后端 → 前端）
interface StrategyMessage {
  type: "strategy"
  demand_analysis: DemandAnalysis
  action_plan: ActionPlan
  constraints: Constraints
  correction_preplan?: CorrectionPreplan
}

// 2. 纠正指令（后端 → 前端）
interface CorrectionMessage {
  type: "correction"
  level: "soft" | "hard"
  method: "append" | "replace_queued" | "retract" | "redirect"
  bubbles?: BubbleTemplate[]    // 要追加/替换的气泡
  retract_count?: number        // 撤回最近N个气泡（仅 queued）
  transition?: string           // 改口过渡语，如 "让我再想想..."
}

// 3. 话题切换（后端 → 前端）
interface HandoffMessage {
  type: "handoff"
  from_agent: string
  to_agent: string
  reason: string
  transition_bubble: string     // 过渡气泡，如 "说到这个，其实我想了解一下..."
}

// 4. 行为约束更新（后端 → 前端）
interface ConstraintMessage {
  type: "constraint"
  tone?: string
  max_bubbles_per_burst?: number
  avoid_topics?: string[]
  pause_work?: boolean
}

// 5. 完整气泡覆盖（后端 → 前端，用于纠正已发送内容）
interface ContentOverrideMessage {
  type: "content_override"
  target_bubble_id?: string     // 要覆盖的气泡ID（不填则覆盖最后一个）
  new_content: string           // 新内容
  transition: string            // 过渡语，如 "不好意思，我更正一下..."
}

// 6. 前端行为报告（前端 → 后端）
interface BehaviorReportMessage {
  type: "behavior_report"
  action: "bubble_sent" | "bubble_queued" | "bubble_retracted" | "user_stopped"
  bubble_id: string
  bubble_content: string
  queue_depth: number           // 剩余排队气泡数
  timestamp: number
}

// 7. 干预指令（后端 → 前端，紧急情况）
interface InterventionMessage {
  type: "intervention"
  priority: "immediate" | "after_current_bubble"
  action: "stop" | "clear_queue" | "send_specific" | "handoff"
  specific_bubble?: string      // send_specific 时的指定内容
  reason: string
}
```

```
t=14.0s   气泡5 发送（后端planned）

          ═══════════ 纠正场景 ═══════════
          假设前端气泡3 偏离了方向：

t=6.1s    S→C correction: {
            level: "soft",
            method: "append",
            bubbles: [
              { content: "嗯等等，其实我更想先了解一下..." }
            ],
            transition: "补充一下"
          }
          → 前端追加一个"改口"气泡，自然修正方向
```

## 六、纠正与干预机制

### 6.1 纠正级别

| 级别 | 触发条件 | 行为 | 用户感知 |
|---|---|---|---|
| **Soft** | 轻微偏离，补充信息 | 追加引导气泡 | "嗯，我再补充一下..." |
| **Hard** | 明显方向错误 | 替换 queued 气泡 + 追加改口 | "不好意思，我更正一下..." |
| **Intervention** | 危机/严重错误 | 清空队列 + 立即重定向 | 自然转折，不显机械 |

### 6.2 改口机制（自然纠正）

核心原则：**永远不出现"我收回刚才的话"这种机械纠正**。所有纠正都以自然对话方式呈现。

```typescript
const CORRECTION_TRANSITIONS = {
  soft_add: [
    "对了，还有一点...",
    "补充一下～",
    "另外我想说的是...",
  ],
  soft_redirect: [
    "嗯等等，我换个角度想...",
    "其实换个思路...",
  ],
  hard_correct: [
    "不好意思，我刚才没说清楚",
    "让我重新整理一下思路...",
    "等一下，我仔细想想...",
  ],
  emotion_catchup: [
    "而且我注意到你好像有点{emotion}...",
    "先不说这个，我感觉你现在{emotion}...",
  ],
}
```

### 6.3 三气泡分类与纠正能力

```
┌──────────┬──────────┬─────────────────────┐
│  气泡状态  │ 用户可见  │      纠正方式         │
├──────────┼──────────┼─────────────────────┤
│  sent    │   ✓ 已见  │ 只能：追加改口气泡    │
│          │          │ 不能：修改/删除       │
├──────────┼──────────┼─────────────────────┤
│  queued  │   ✗ 未发  │ 可以：替换/修改/删除  │
│          │          │ 可以：调整顺序        │
├──────────┼──────────┼─────────────────────┤
│ planned  │   ✗ 未发  │ 可以：完全控制        │
│          │          │ 由后端策略指定        │
└──────────┴──────────┴─────────────────────┘
```

### 6.4 冲突解决原则

**后端总是赢（Director always wins），但后端从不直接替换文本。**

具体实现：
1. **Sent 气泡发生错误** → 后端让前端追加一个"改口"气泡，用自然过渡语
2. **Queued 气泡有更好的版本** → 后端直接替换内容，前端无感
3. **Planned 区域由后端完全控制** → 前端只负责渲染

## 七、自主度梯度

前端 Actor 的自主度不是固定的，随着对话深入而变化：

```
自主度
  ↑
100% ┤                    ┌──────────────
    ┤                  ╱
 80% ┤              ╱
    ┤            ╱    ← 后端策略稳定，前端自主维持续航
 50% ┤        ╱
    ┤     ╱
 30% ┤  ╱
    ┤╱    ← 刚接入，等待后端初始策略
  0% ┼────┬────┬────┬────┬──────→ 对话轮次
        R1   R2   R3   R4   R5+

  阶段1: 低自主度 — 等待后端首次策略，气泡以 queued 状态堆积
  阶段2: 中自主度 — 后端策略返回，前端按计划执行 + 自行处理简单追问
  阶段3: 高自主度 — 话题稳定，前端自主生成大部分气泡，后端进入监控模式
  阶段4: 监控模式 — 后端降频检查，仅在偏差时介入
```

**实现**：

```typescript
interface AutonomyState {
  level: "low" | "medium" | "high"
  strategyReceived: boolean
  consecutiveCorrectBubbles: number  // 连续正确气泡数，达到阈值升级自主度
  lastCorrectionTime: number         // 上次被纠正的时间
}

function calculateAutonomy(state: AutonomyState): number {
  if (!state.strategyReceived) return 0.2           // 无策略，极低自主度
  if (Date.now() - state.lastCorrectionTime < 30000) return 0.4  // 刚被纠正
  if (state.consecutiveCorrectBubbles > 10) return 0.9 // 高自主
  if (state.consecutiveCorrectBubbles > 5) return 0.7  // 中自主
  return 0.5                                             // 基础自主
}
```

## 九、设计决策记录

### 决策1：前端分类用关键词而非小模型

**选择**：基于关键词+规则的 IntentClassifier
**原因**：
- 加载一个小模型（如 ONNX 模型）增加前端体积和首屏时间
- 关键词匹配与后端 `_simulate_demand_analysis` 保持一致，便于对照
- 5ms 内完成分类，不给用户任何等待感知
- 分类错误可以被后端 strategy 纠正，容错率高

### 决策2：后端输出策略而非文本

**选择**：StrategyPlanner 输出 JSON 行为序列，不是自然语言回复
**原因**：
- LLM token 消耗更低（行为描述比完整回复短）
- 前端有更大的灵活度（模板选择、发送时机）
- 后端与前端解耦（改模板不需要后端配合）

### 决策3：纠正通过自然改口而非直接替换

**选择**：Sent 气泡不删除不修改，追加过渡语+新内容
**原因**：
- 直接替换 sent 气泡会被用户察觉
- 真人聊天改口是追加说明，不是编辑历史
- 保留对话的"瑕疵感"反而增加真实感

### 决策4：前端主导气泡节奏，后端主导方向

**选择**：前端决定何时发气泡、打字速度；后端决定发什么内容
**原因**：
- 打字节奏对网络延迟敏感，前端控制响应快
- 内容正确性依赖深度理解，后端控制更准确
- 职责边界清晰，减少耦合
