# 前后端快慢思考架构（Talker-Thinker Pattern）

## 一、核心思想

### 1.1 问题背景

当前架构中，用户发消息 → 后端 LLM 深度思考 → 生成完整回答 → 前端一次性渲染。存在两个体验问题：

1. **等待时间过长**：DeepSeek API 深度需求分析 + 下游智能体生成回答，数秒到数十秒的空白等待
2. **替换式修正很机械**：后端生成完整回答后替换前端占位内容，用户能感知到"被替换"，不像真人聊天

### 1.2 设计理念：Talker-Thinker 模式（双模型协同）

仿照人类微信聊天行为——**前端用轻量模型快速响应用户，保持对话流畅；后端用深度模型异步分析，产出聊天大纲指导后续对话方向**。

```
┌──────────────────────────────────────────────────────────────────┐
│                    Talker-Thinker 双模型架构                        │
│                                                                  │
│  Talker (轻量模型)               Thinker (深度模型)        │
│  ┌──────────────────────┐          ┌──────────────────────────┐  │
│  │ 响应时间: 2-3s        │          │ 响应时间: 5-15s            │  │
│  │ 模型: 本地小模型/模板  │   WS    │ 模型: DeepSeek API         │  │
│  │                      │◄───────►│                          │  │
│  │ • 意图快速分类        │          │ • 对话历史深度分析          │  │
│  │ • 即时回复生成        │          │ • 情绪累积评估             │  │
│  │ • 打字模拟            │          │ • 聊天大纲生成             │  │
│  │ • 大纲执行            │          │ • 追问/跳过决策            │  │
│  │ • 话题自然过渡        │          │ • 前端行为监控             │  │
│  └──────────────────────┘          └──────────────────────────┘  │
│                                                                  │
│  类比：Talker 在台上与用户互动（快速回应），Thinker 在后台观察全局、       │
│  递纸条调整方向（异步分析）。Talker 不等 Thinker 完整剧本，先开口；         │
│  Thinker 看准时机给出大纲，Talker 自然地融入后续对话。                      │
└──────────────────────────────────────────────────────────────────┘
```

**核心区别**：Talker 负责"说"，Thinker 负责"想"——想好了把大纲给 Talker，Talker 融进接下来的对话里。

### 1.3 双模型协同表

| | Talker (轻量模型) | Thinker (深度模型) |
|---|---|---|
| **定位** | 快思考 — 直觉、即时 | 慢思考 — 理性、深度 |
| **延迟** | 2-3s | 5-15s (异步，不阻塞) |
| **模型** | 本地轻量模型 / 模板引擎 | DeepSeek API (深度推理) |
| **输入** | 用户最新消息 + 当前大纲 | 完整对话历史 (批量) |
| **产出** | 即时回复气泡 | 聊天大纲 (ChatOutline JSON) |
| **触发** | 每次用户发消息 | 批量触发 (计数/定时/静默) |
| **失败处理** | 降级到模板回复 | 丢弃过期结果，等待下次触发 |

### 1.4 认知科学基础：Kahneman 双系统理论

| | System 1 (快思考) | System 2 (慢思考) |
|---|---|---|
| **位置** | 前端 | 后端 |
| **特点** | 直觉、自动、快速 | 理性、刻意、缓慢 |
| **延迟** | 2-3s | 5-15s (异步) |
| **能力** | 模式匹配、模板填充、自然接话 | 深度推理、情绪分析、策略规划 |
| **产出** | 聊天气泡 | 聊天大纲 + 指导方向 |

## 二、架构总览

### 2.1 数据流图

```
用户输入 "我明天有个面试，好紧张"
        │
        ▼
┌──────────────────────────────────────────────────┐
│                  WebSocket 网关                    │
│         ws://localhost:8080/ws/{sessionId}        │
└──────────────────────────────────────────────────┘
        │                               │
        ▼ 立即处理                       ▼ 异步批量处理
┌──────────────────────┐       ┌──────────────────────────┐
│  Talker 轻量引擎         │       │  Thinker 深度引擎          │
│                      │       │                          │
│ 1. IntentClassifier  │       │ 1. MessageBuffer 累积消息  │
│    3类快速分类        │       │                          │
│ 2. TemplateResponder │       │ 2. 触发条件检查             │
│    生成即时回复        │       │    • 消息数 ≥ 10条         │
│ 3. TypingSimulator   │       │    • 定时器 ≥ 30s         │
│    模拟打字发送        │       │    • 静默 ≥ 3s           │
│                      │       │                          │
│ 产出: 即时气泡 (2-3s) │       │ 3. DeepSeek 深度分析       │
│ "面试确实让人紧张呢~"  │       │    情绪 + 话题 + 追问决策   │
│                      │       │                          │
│                      │       │ 4. ChatOutline 生成        │
│                      │       │    版本化，含有效范围        │
└──────────────────────┘       └──────────────────────────┘
        │                               │
        │  用户已看到回复，开始阅读        │  分析完成后通过 WS 下发
        │  对话继续进行                  │  outline 消息
        │                               ▼
        │                      ┌──────────────────────────┐
        │                      │   前端 OutlineExecutor     │
        │                      │                          │
        │                      │ • 检查 outline 是否过期     │
        │                      │ • 融入后续对话方向         │
        │                      │ • 自然追问建议中的问题      │
        │                      │ • 避开大纲标记的雷区       │
        └──────────────────────┴──────────────────────────┘
```

**关键时序**：
- t=0ms: 用户发消息
- t=2-3s: 前端轻量模型完成回复，用户开始阅读
- t=3-30s: 后端在后台异步分析（用户无感知）
- t=30s+: 后端产出大纲，前端在接下来的对话中自然融入

### 2.2 角色职责

#### Talker（轻量模型）

| 职责 | 说明 |
|---|---|
| **意图分类** | 基于轻量模型的 3 类快速分类（crisis / simple / normal），≤500ms |
| **即时回复** | 生成自然、温暖的简短回复（2-3s 内完成） |
| **打字模拟** | 逐字/逐词渲染，随机 typing 延迟，模拟真人输入节奏 |
| **大纲执行** | 接收后端下发的 ChatOutline，自然融入后续对话方向 |
| **话题过渡** | 在 outline 指导下平滑切换话题，不生硬转折 |
| **状态展示** | 显示后端分析进度（"情绪分析中..."等真实阶段） |

#### Thinker（深度模型）

| 职责 | 说明 |
|---|---|
| **消息缓冲** | 持续接收全部对话消息，维护未分析区间 |
| **批量触发** | 3 条件并行触发深度分析（计数/定时/静默） |
| **深度分析** | DeepSeek API 驱动的情绪评估 + 话题分析 + 追问决策 |
| **大纲生成** | 将分析结果转化为 ChatOutline（版本化、含有效范围） |
| **过期检测** | 大纲落后当前消息数 >20 条则丢弃，等待下次触发 |
| **进度上报** | 分析过程中通过 status 消息同步真实阶段 |
| **长期记忆** | 维护 ConversationContext，累积情绪状态，识别模式 |

## 三、前端快思考：轻量交互引擎

### 3.1 架构设计

```
LightweightEngine
├── IntentClassifier      # 意图分类器（轻量模型，3 分类）
├── TemplateResponder     # 即时回复生成器
├── TypingSimulator       # 打字模拟器（延迟、逐字输出）
├── OutlineExecutor       # 大纲执行器（接收并融入后端大纲）
├── StatusDisplay         # 后端分析状态展示
└── CrisisHandler         # 危机检测与升级
```

### 3.2 意图分类器（IntentClassifier）

简化为 3 分类，降低分类负担，把深度判断留给后端：

```typescript
enum IntentClass {
  CRISIS  = "crisis",   // 危机信号：立即升级，停止正常回复
  SIMPLE  = "simple",   // 简单问候/感谢/确认，模板即可覆盖
  NORMAL  = "normal",   // 正常对话：需要后端深度分析，先用轻量回复过渡
}

// 关键词辅助 + 轻量模型确认
function classifyIntent(input: string, context: ConversationContext): IntentClass {
  // 第一层：关键词快速筛查（≤10ms）
  if (hasCrisisSignal(input)) return IntentClass.CRISIS

  // 第二层：模式匹配简单对话（≤50ms）
  if (isSimpleGreeting(input)) return IntentClass.SIMPLE

  // 第三层：轻量模型推理（≤500ms）
  // 小模型判断是否为简单寒暄，其余归为 normal
  return lightweightModel.classify(input, context.lastMessages(3))
}

const CRISIS_KEYWORDS = [
  "不想活了", "绝望", "崩溃了", "撑不下去", "自杀", "自残"
]

const SIMPLE_PATTERNS = [
  /^(好的|谢谢|嗯|哦|知道了|明白了)[!！。.]?$/,
  /^(早安|晚安|你好|嗨|hi|hello)[!！。.]?$/i,
  /^(拜拜|再见|回头聊|下次聊)[!！。.]?$/,
]
```

**要点**：
- 危机信号优先检测（安全第一），不经过模型直接触发升级
- 3 分类降低前端模型负担，分类结果 ≤500ms
- 分类错误可被后端 outline 纠正，容错率高
- 大部分消息归为 NORMAL——"前端先回着，后端慢慢想"

### 3.3 即时回复生成器（TemplateResponder）

按意图分类生成不同的即时回复：

```typescript
interface QuickReply {
  bubbles: string[]           // 1-3 个气泡
  typingStyle: "casual" | "caring" | "professional"
  estimatedDuration: number   // 预估打字总时长 (ms)
}

const RESPONDER_STRATEGY: Record<IntentClass, ResponderFn> = {
  crisis: (input, ctx) => ({
    // 危机：不闲聊，直接引导寻求专业帮助
    bubbles: [
      "我听到了你的感受，这很重要。",
      "请立即联系专业心理支持热线：12320-5（24小时）",
      "我在这里陪着你，但我们先确保你获得专业帮助，好吗？"
    ],
    typingStyle: "caring",
    estimatedDuration: 8000,
  }),

  simple: (input, ctx) => ({
    // 简单对话：轻量模型生成简短回复
    bubbles: [lightweightModel.generate(input, ctx)],
    typingStyle: "casual",
    estimatedDuration: 2000,
  }),

  normal: (input, ctx) => ({
    // 正常对话：轻量模型生成过渡性回复
    // 目的是让用户不等待，同时为后端分析争取时间
    // 回复风格：承接话题 + 简短共情 + 轻度追问
    bubbles: lightweightModel.generateBrief(input, ctx, {
      maxBubbles: 2,
      maxTokens: 80,
      tone: ctx.currentOutline?.avoid?.tones
        ? avoidTones(ctx.currentOutline.avoid.tones)
        : "warm_professional",
    }),
    typingStyle: "warm_professional",
    estimatedDuration: 4000,
  }),
}
```

**Normal 回复的设计原则**：
- 不深入分析（留给后端），只做情感承接和轻度追问
- 回复偏"开放"，给后端大纲留下调整空间
- 每条约 20-40 字，自然不做作
- 示例："面试确实容易让人紧张呢～你先说说看是什么岗位？"

### 3.4 打字模拟器（TypingSimulator）

即使前端回复只需 2-3s 生成，打字模拟仍然保留——这是体验层，不是性能层。

```typescript
interface TypingConfig {
  charsPerTick: number        // 每次吐出字数 (1-3)
  tickInterval: number        // 基础间隔(ms) (60-150)
  variability: number         // 随机波动 (0.3 = ±30%)
  pausePunctuation: number    // 标点符号处额外停顿(ms) (200-600)
  longMessageThreshold: number // 超过此长度拆分气泡 (40字)
  bubbleInterval: number      // 气泡间间隔(ms) (600-1500)
}

const DEFAULT_TYPING_CONFIG: TypingConfig = {
  charsPerTick: 2,
  tickInterval: 100,
  variability: 0.3,
  pausePunctuation: 400,
  longMessageThreshold: 40,
  bubbleInterval: 1000,
}
```

**关键行为**：
- 超过 `longMessageThreshold` 的文字自动拆分为新气泡
- 标点符号处增加停顿，模拟真人思考
- 气泡间间隔 600-1500ms，模拟阅读+打字时间
- 用户发消息后立即开始"正在输入"动画，无空白期

### 3.5 大纲执行器（OutlineExecutor）

接收后端下发的 ChatOutline，自然融入后续对话：

```typescript
interface OutlineExecutor {
  // 处理新到达的大纲
  receiveOutline(outline: ChatOutline): void

  // 在生成下一条回复前，检查大纲指导
  getGuidance(userInput: string): OutlineGuidance

  // 判断大纲是否过期
  isStale(outline: ChatOutline): boolean
}

interface OutlineGuidance {
  // 推荐追问的问题（从 follow_up_suggestions 中选）
  suggestedQuestions: string[]

  // 当前应避开的话题
  avoidTopics: string[]

  // 当前应避开的语气
  avoidTones: string[]

  // 对话大方向描述（融入到 System Prompt 中）
  directionHint: string
}

// 大纲融入策略：
// 1. 不在收到大纲后立刻切换话题（等用户自然停顿）
// 2. 不在气泡中间插入大纲内容（等当前回复完成）
// 3. 下一个对话回合中，在 TemplateResponder 的 prompt 中注入 directionHint
// 4. 从 suggestedQuestions 中选最自然的时机追问
```

**大纲注入时机判断**：
```
用户发言 → 前端检测到静默窗口 ≥ 2s
         → 且当前没有排队中的回复
         → 且大纲中有 must_follow_up 未处理
         → 在新回复中自然融入追问
```

## 四、后端慢思考：异步大纲引擎

### 4.1 核心转变：从同步生成到异步分析

```
旧模式（Answer Generator）：
  用户输入 → DeepSeek API → 完整回答文本 → 前端渲染
  问题：用户等待时间长，无法处理连续快速对话

新模式（Async Outline Engine）：
  用户输入 → 前端立即回复（2-3s）
  多条消息 → 累积到 MessageBuffer → 触发条件满足 → DeepSeek 批量分析
  → 产出 ChatOutline（版本化）→ 前端融入后续对话
```

后端不再直接生成回答文本，而是产出**聊天大纲**，前端按大纲自主回复。

### 4.2 消息缓冲池（MessageBuffer）

持续接收消息，维护已分析/未分析边界：

```python
class MessageBuffer:
    """消息缓冲池——持续累积，批量分析"""

    STALE_THRESHOLD = 20  # 大纲过期阈值：落后 20 条即丢弃

    def __init__(self):
        self.messages: list[Message] = []
        self.last_analyzed_index: int = -1  # 最后一条已分析的消息索引
        self.latest_outline: ChatOutline | None = None

    def append(self, msg: Message) -> None:
        """追加消息到缓冲池"""
        self.messages.append(msg)

    def get_unanalyzed(self) -> list[Message]:
        """获取所有未分析的消息"""
        return self.messages[self.last_analyzed_index + 1:]

    def get_unanalyzed_count(self) -> int:
        """未分析消息数量"""
        return len(self.messages) - self.last_analyzed_index - 1

    def mark_analyzed(self, up_to_index: int) -> None:
        """标记消息已被分析"""
        self.last_analyzed_index = up_to_index

    def get_context_window(self, size: int = 50) -> list[Message]:
        """获取最近 N 条消息作为分析上下文"""
        return self.messages[-size:]

    def total_count(self) -> int:
        return len(self.messages)
```

### 4.3 三触发机制

三种触发器并行运行，任一满足即启动分析：

```
┌─────────────────────────────────────────────────────────────┐
│                     三触发机制（并行检测）                      │
│                                                             │
│  触发器 1: 消息计数                                           │
│  ├── 条件: get_unanalyzed_count() ≥ 10                       │
│  ├── 场景: 用户连续快速聊天，10条后必然触发                     │
│  └── 行为: 立即启动分析                                       │
│                                                             │
│  触发器 2: 定时器                                             │
│  ├── 条件: 距上次分析 ≥ 30s                                   │
│  ├── 场景: 用户聊天节奏慢，30s 没分析就强制触发                  │
│  └── 行为: 立即启动分析（即使未分析消息 < 10 条）               │
│                                                             │
│  触发器 3: 静默窗口                                           │
│  ├── 条件: 用户 ≥ 3s 未发新消息                               │
│  ├── 场景: 用户可能在看前端回复，正是分析的好时机                │
│  └── 行为: 启动分析（但不强制，优先使用前两个触发器的结果）        │
│                                                             │
│  防重复: 分析进行中时不重复触发；分析完成后重置所有计时器         │
└─────────────────────────────────────────────────────────────┘
```

```python
class AnalysisTrigger:
    """异步分析触发器"""

    def __init__(self, buffer: MessageBuffer, analyzer: AsyncAnalyzer):
        self.buffer = buffer
        self.analyzer = analyzer
        self.analyzing = False
        self.last_analysis_time = time.time()

    async def on_new_message(self) -> None:
        """每次新消息到达时检查触发条件"""
        if self.analyzing:
            return  # 分析进行中，不重复触发

        count = self.buffer.get_unanalyzed_count()
        elapsed = time.time() - self.last_analysis_time

        if count >= 10:
            await self._start_analysis("count_trigger")
        elif elapsed >= 30 and count > 0:
            await self._start_analysis("timer_trigger")

    async def on_silence_detected(self, silence_duration: float) -> None:
        """静默检测（由前端 behavior_report 或服务端计时器驱动）"""
        if self.analyzing:
            return

        if silence_duration >= 3.0 and self.buffer.get_unanalyzed_count() > 0:
            await self._start_analysis("silence_trigger")

    async def _start_analysis(self, trigger: str) -> None:
        self.analyzing = True
        try:
            result = await self.analyzer.analyze(
                messages=self.buffer.get_context_window(),
                unanalyzed=self.buffer.get_unanalyzed(),
            )
            self.buffer.mark_analyzed(self.buffer.total_count() - 1)
            self.last_analysis_time = time.time()
            await self._dispatch_outline(result)
        finally:
            self.analyzing = False
```

### 4.4 聊天大纲（ChatOutline）

后端产出的核心数据结构：

```typescript
interface ChatOutline {
  type: "outline"
  version: number                     // 递增版本号

  // 此大纲基于的消息范围
  based_on_message_range: {
    start_index: number
    end_index: number
  }

  // 生成时间戳
  generated_at: number

  // 对话状态摘要
  conversation_state: {
    emotion_primary: string           // 主要情绪：anxiety / stress / confused / confident / neutral
    emotion_intensity: "low" | "medium" | "high"
    emotion_trend: "improving" | "stable" | "worsening"
    current_topic: string             // 当前主要话题
    topic_progress: number            // 话题完成度 0-100
    should_defer_work: boolean        // 是否应暂停工作话题，优先情绪支持
  }

  // 追问建议（分优先级）
  follow_up_suggestions: {
    must: FollowUpItem[]              // 必须追问的关键信息
    should: FollowUpItem[]            // 建议追问
    optional: FollowUpItem[]          // 可选的延伸话题
  }

  // 需要避开的
  avoid: {
    topics: string[]                  // 暂时避开的话题（如用户情绪低落时避免谈面试压力）
    tones: string[]                   // 暂时避开的语气（如避免太正式/太轻快）
  }

  // 下一阶段方向
  next_direction: string              // 自然语言描述，注入前端 System Prompt
}

interface FollowUpItem {
  question: string                    // 建议追问的问题
  reason: string                      // 追问原因（供前端判断时机）
  priority: number                    // 优先级 1-10
  depends_on_context?: string         // 追问条件（如 "等用户提到项目经验后"）
}
```

### 4.5 异步分析流程

```
未分析消息 → DeepSeek API 调用

Step 1: 情绪累积评估
  ├── 逐条分析最新消息的情绪倾向
  ├── 结合历史情绪数据（ConversationContext）
  ├── 计算情绪趋势（improving / stable / worsening）
  └── 判断是否需要暂停工作话题
      输出: emotion_primary, emotion_trend, should_defer_work

Step 2: 话题与需求分析
  ├── 识别当前主要话题
  ├── 判断话题完成度（用户是否已经说清楚了）
  ├── 发现信息缺口（哪些关键信息用户还没说）
  └── 区分需追问 vs 可不问的问题
      输出: current_topic, topic_progress, follow_up_suggestions

Step 3: 雷区标记
  ├── 如果情绪低落 → avoid.topics 加入压力源话题
  ├── 如果用户表现防御 → avoid.tones 加入 overly_professional
  └── 如果对话偏离主线 → next_direction 引导回归
      输出: avoid.topics, avoid.tones, next_direction

Step 4: 组装 ChatOutline
  ├── 赋予新版本号
  ├── 记录 based_on_message_range
  └── 通过 WebSocket 发送 outline 消息
```

```python
class AsyncAnalyzer:
    """异步深度分析器"""

    async def analyze(
        self,
        messages: list[Message],
        unanalyzed: list[Message],
    ) -> ChatOutline:
        # 构建分析 prompt
        prompt = self._build_analysis_prompt(messages, unanalyzed)

        # 调用 DeepSeek API（5-15s）
        response = await self.llm.agenerate(prompt)

        # 解析为 ChatOutline
        outline = self._parse_outline(response)
        outline.version = self._next_version()
        outline.generated_at = time.time()
        outline.based_on_message_range = {
            "start_index": messages[0].index if messages else 0,
            "end_index": messages[-1].index if messages else 0,
        }

        return outline
```

### 4.6 大纲版本管理与过期检测

```python
class OutlineManager:
    """大纲版本管理"""

    STALE_THRESHOLD = 20  # 大纲覆盖范围落后 20 条消息即视为过期

    def __init__(self):
        self.current_outline: ChatOutline | None = None

    def should_override(self, new_outline: ChatOutline) -> bool:
        """判断新大纲是否应覆盖当前大纲"""
        if self.current_outline is None:
            return True
        # 版本号更高的覆盖
        return new_outline.version > self.current_outline.version

    def is_stale(self, outline: ChatOutline, current_message_count: int) -> bool:
        """判断大纲是否已过期"""
        covered_end = outline.based_on_message_range.end_index
        lag = current_message_count - covered_end
        return lag > self.STALE_THRESHOLD

    def get_active_outline(self, current_message_count: int) -> ChatOutline | None:
        """获取当前有效大纲（自动丢弃过期）"""
        if self.current_outline is None:
            return None
        if self.is_stale(self.current_outline, current_message_count):
            self.current_outline = None  # 丢弃过期大纲
            return None
        return self.current_outline
```

**过期处理策略**：
- 大纲过期 → 直接丢弃，不通知前端
- 前端检测到 outline 被清空 → 回归纯 TemplateResponder 模式
- 后端下次触发会自动生成新大纲
- 用户无感知——前端回复不会突变

## 六、纠正与干预机制

### 6.1 纠正策略：大纲引导而非直接替换

新架构下，纠正不再通过"改口"气泡实现，而是通过**大纲更新**自然引导：

| 场景 | 旧方案（Talker-Thinker v1） | 新方案（双模型） |
|---|---|---|
| 前端回复方向偏了 | 后端发 correction，前端追加改口气泡 | 后端更新 outline.avoid 和 next_direction，前端下一条回复自然调整 |
| 用户情绪被忽略 | 后端发 intervention，前端暂停并改口 | 后端更新 outline.conversation_state.should_defer_work = true，前端下条回复切换为情绪支持 |
| 话题推进过快 | 后端发 constraint，限制前端行为 | 后端降低 outline.topic_progress，增加 must_follow_up |
| 危机信号 | 立即升级 | 同：前端直接升级，不依赖大纲（crisis 分类优先） |

### 6.2 大纲引导的优势

```
旧方案问题：
  后端发 correction → 前端追加"改口"气泡
  → 用户: "嗯？刚才不是这么说的"
  → 有"被纠正"的感知

新方案：
  后端更新 outline → 前端下一条回复自然调整方向
  → 用户: "哦对，接着说"（感觉像是 AI 自己想起来了）
  → 无纠正感，对话流自然
```

### 6.3 干预升级路径

```
Level 1: 大纲微调（默认）
  触发: 轻微偏差
  行为: 更新 next_direction + avoid
  用户感知: 无（下一条回复自然调整）

Level 2: 大纲强制刷新
  触发: 明显方向偏差
  行为: 立即触发一次新分析，覆盖当前大纲
  用户感知: 无（前端回复逐渐变化）

Level 3: 前端直接干预（紧急）
  触发: 危机信号 / should_defer_work 突变
  行为: 通过 status 消息提示前端切换模式
  用户感知: 回复风格明显转变（从专业→关怀）

Level 4: 人工介入
  触发: 持续危机信号 > 3 轮
  行为: 前端显示专业支持热线，后端告警
  用户感知: 明确的"我需要帮你找到真人支持"
```

### 6.4 冲突解决原则

**大纲总是赢（Thinker always wins），但 Talker 决定"怎么赢"。**

| 冲突场景 | 解决方式 |
|---|---|
| 大纲说"追问A"，用户已经回答了A | 前端跳过，下一个气泡用大纲的下一个建议 |
| 大纲说"避开话题X"，用户主动提起X | 前端不避开（用户主导），但回复偏中性 |
| 大纲过期了 | 前端回归纯 TemplateResponder，等新大纲 |
| 前端生成回复时大纲更新了 | 如果当前气泡未发送（queued），融入新大纲；如果已发送（sent），下条调整 |

## 七、自主度梯度

Talker 的自主度随大纲新鲜度和对话阶段动态变化：

```
自主度
  ↑
100% ┤                    ┌──────────────────
    ┤                  ╱
 80% ┤              ╱        ← 大纲稳定，前端自主维持续航
    ┤            ╱              high autonomy
 60% ┤        ╱
    ┤     ╱    ← 大纲到达，前端按大纲调整
 40% ┤  ╱         medium autonomy
    ┤╱
 20% ┤← 无大纲，纯模板模式
    ┤  low autonomy
  0% ┼────┬────┬────┬────┬──────→ 对话轮次
        R1   R2   R3   R4   R5+

  阶段1: 低自主度 — 无大纲，TemplateResponder 独立工作
  阶段2: 中自主度 — 初版大纲到达，前端开始融入方向
  阶段3: 高自主度 — 大纲多轮更新后趋于稳定，前端自主发挥空间增大
  阶段4: 稳态    — 后端降频分析，仅在检测到变化时更新大纲
```

```typescript
interface AutonomyState {
  level: "low" | "medium" | "high"

  // 大纲相关
  hasOutline: boolean
  outlineAge: number               // 大纲生成后的时间 (ms)
  outlineVersion: number
  outlineStaleness: number         // 大纲覆盖范围落后消息数

  // 纠正相关
  consecutiveStableRounds: number  // 连续未被大纲调整的轮数
  lastOutlineUpdateTime: number
}

function calculateAutonomy(state: AutonomyState): number {
  if (!state.hasOutline) return 0.3           // 无大纲，30% 自主（纯模板）
  if (state.outlineStaleness > 15) return 0.4 // 大纲快过期了，降自主等新大纲
  if (state.consecutiveStableRounds > 10) return 0.9  // 高度稳定
  if (state.consecutiveStableRounds > 5) return 0.7   // 中等稳定
  return 0.5                                            // 基础自主
}
```

**后端降频策略**：
- 高自主度时，调整触发条件：消息计数阈值从 10 → 20，定时器从 30s → 60s
- 检测到情绪波动时立即恢复高频分析

## 九、设计决策记录

### 决策1：前端用轻量模型 + 模板，而非纯关键词

**选择**：轻量模型 + 规则兜底
**原因**：
- 纯关键词匹配太僵硬，无法处理自然语言的变化
- 轻量模型（2-3s）提供比模板更好的回复质量
- 模型失败时降级到模板，确保可用性
- 3 分类（crisis/simple/normal）足够简单，模型负担小

### 决策2：后端异步批量分析，而非每条消息都分析

**选择**：三触发机制（计数/定时/静默）批量分析
**原因**：
- 逐条分析浪费 API 调用，用户快速聊天时后端频繁被打断
- 批量分析能看到更完整的对话图景
- 三触发保证不会遗漏（用户不停聊 10 条触发，聊得慢 30s 触发，停了 3s 触发）
- 异步不阻塞前端回复

### 决策3：后端输出大纲而非回复文本

**选择**：ChatOutline JSON 替代完整回复
**原因**：
- LLM token 消耗更低（大纲描述比完整回复短）
- 前端有更大灵活度（决定什么时候追问、用什么样的措辞）
- 后端与前端解耦（改回复风格不需要后端配合）
- 大纲版本化确保前端不会用过期指导

### 决策4：大纲融入而非直接替换

**选择**：大纲通过 System Prompt 融入前端下一条回复
**原因**：
- 直接替换气泡会被用户察觉（"刚才不是这么说的"）
- 大纲融入是渐进的，用户无感知
- 真人聊天改方向是自然的（"对了，说起这个..."）
- 保留对话的连续性

### 决策5：过期大纲直接丢弃

**选择**：大纲落后 >20 条消息即丢弃，不尝试追赶
**原因**：
- 追赶过期大纲可能引入过时的方向，反而误导
- 前端回归模板模式（低自主度）是安全的降级
- 后端下次触发会自动生成新大纲
- 简单规则，减少 bug 面

### 决策6：打字模拟保留（即使前端回复只需 2-3s）

**选择**：保留 TypingSimulator
**原因**：
- 打字模拟是体验层，不是性能层
- 即使生成只需 2s，逐字显示也比一次性弹出更自然
- 打字过程给用户阅读时间
- 给后端分析争取额外时间窗口
