# OpenCareer 记忆系统方案

## 1. 概述

OpenCareer 记忆系统是一个**混合记忆架构**，结合向量记忆与结构化记忆，实现对话上下文、用户画像、简历数据的持久化存储与语义检索。系统以**被动提取**为核心设计理念——用户无需主动填写表单，系统在与用户的自然对话中自动识别、提取并存储简历相关信息。

### 1.1 核心设计目标

| 目标 | 说明 |
|------|------|
| **被动采集** | 不主动追问，用户在对话中提及的信息自动提取 |
| **增量更新** | 只记录变化部分，避免重复和覆盖已有数据 |
| **语义检索** | 支持通过自然语言查询历史对话和用户画像 |
| **混合存储** | 向量数据库支持语义搜索，结构化数据库支持精确查询 |
| **情感感知** | 模型能感知用户情绪状态并影响路由决策 |

### 1.2 四层架构

```
用户对话
    │
    ▼
┌────────────────────────────────────────────────────┐
│  Extraction Layer  (被动提取层)                      │
│  resume_extractor.py  ·  LLM-powered delta extract  │
└───────────────────────┬────────────────────────────┘
                        │ delta
                        ▼
┌────────────────────────────────────────────────────┐
│  Data Layer  (数据层)                               │
│  ConversationContext.user_profile["resume_data"]    │
│  内存中的每个用户的当前数据                            │
└───────────────────────┬────────────────────────────┘
                        │ save / load
                        ▼
┌────────────────────────────────────────────────────┐
│  Persistence Layer  (持久化层)                       │
│  ResumeStore  →  structured_memory (JSON / SQLite)  │
│  MemoryManager  →  vector_memory (ChromaDB)         │
└───────────────────────┬────────────────────────────┘
                        │
                        ▼
┌────────────────────────────────────────────────────┐
│  Schema Layer  (模式层)                             │
│  resume_schema.py  ·  字段定义 · 校验规则 · 枚举      │
└────────────────────────────────────────────────────┘
```

## 2. Schema 层 — 数据结构定义

文件：`memory/resume_schema.py`

Schema 层定义了完整的简历数据模型，涵盖 7 个模块、约 30 个字段。

### 2.1 模块与标签

```python
class ResumeModule(str, Enum):
    JOB_INTENT = "job_intent"              # 求职意向定位
    PERSONAL_INFO = "personal_info"        # 个人基本信息
    EDUCATION = "education"                # 教育背景
    WORK_EXPERIENCE = "work_experience"    # 工作/实习经历
    PROJECT_EXPERIENCE = "project_experience"  # 项目经历
    SKILLS_CERTIFICATES = "skills_certificates" # 专业技能与证书
    OTHER_INFO = "other_info"              # 其他个性化信息
```

### 2.2 字段定义体系

每个字段使用 `ResumeFieldDef` 类描述：

```python
class ResumeFieldDef:
    key: str              # 机器可读字段名（snake_case）
    label: str            # 中文标签
    field_type: FieldType # STRING / LIST / LIST_DICT / DICT
    required: bool        # 是否为简历生成的必要字段
    module: ResumeModule  # 所属模块
    is_repeating: bool    # 是否为可重复组（如多段教育经历）
    sub_fields: List[ResumeFieldDef]  # 重复组的子字段
    extraction_hint: str  # LLM 提取提示
```

### 2.3 字段分模块清单

#### 模块一：求职意向定位
- `target_position` (必要) — 目标岗位，如「Java后端开发工程师」
- `target_industry` (可选) — 目标行业，如「互联网」
- `target_location` (可选) — 目标地点，如「北京」

#### 模块二：个人基本信息
- `name` (必要), `gender` (必要), `phone` (必要), `email` (必要)
- `photo` (可选), `graduation_date` (可选), `availability` (可选)

#### 模块三：教育背景（重复组）
- `education_list` (必要) — 子字段：school, major, degree, education_period, gpa, relevant_courses, honors

#### 模块四：工作/实习经历（重复组）
- `work_experience_list` (必要) — 子字段：company, department, position, work_period, work_responsibilities, company_industry

#### 模块五：项目经历（重复组）
- `project_experience_list` (必要) — 子字段：project_name, project_role, project_period, project_background, project_content, project_result

#### 模块六：专业技能与证书
- `hard_skills` (字典), `soft_skills` (列表), `language_skills` (字典), `certificates` (列表)

#### 模块七：其他个性化信息
- `personal_summary` (字符串), `portfolio_links` (字典), `other_experiences` (列表)

### 2.4 关键工具函数

```python
new_empty_resume_data()               # 创建空数据模板（默认值）
validate_resume_data(data)            # 校验必要字段是否完备
build_flat_profile_for_llm(data)      # 构建 LLM 可读的平铺摘要
get_schema_summary()                  # 获取人类可读的 schema 概览
get_field_def(key)                    # 按 key O(1) 查找字段定义
```

## 3. 数据层 — 对话上下文

文件：`agents/conversation_context.py`

### 3.1 核心数据结构

`ConversationContext` 是贯穿所有 Agent 的共享上下文：

```
ConversationContext
├── user_id               # 用户标识
├── history               # 对话历史（ConversationTurn 列表）
├── current_agent         # 当前活跃 Agent 名称
├── handoff_stack         # Agent 切换记录
├── emotion_history       # 逐轮情感分析历史
└── user_profile          # 用户画像
    ├── mood_history      # 情绪记录列表
    ├── common_concerns   # 用户常提及的关切话题
    ├── job_search_stage  # 求职阶段
    ├── target_role       # 目标职位
    ├── skill_focus       # 用户想发展的技能
    ├── grade_level       # 年级（如大二、研一）
    ├── major             # 专业
    ├── school            # 学校
    ├── background_summary # 背景摘要（自动生成）
    └── resume_data       # 完整简历数据（Schema + Data 核心）
```

### 3.2 数据生命周期

```
用户消息进入
    │
    ▼
add_turn("user", message)           ── 记录对话轮次
    │
    ▼
_extract_user_profile(message)      ── 正则提取（年级/专业/学校）+ LLM提取（完整简历）
    │
    ▼
record_emotion_analysis(analysis)   ── 记录情绪分析结果
    │
    ▼
resume_store.save(user_id, data)    ── 持久化到结构化存储
```

### 3.3 序列化与反序列化

`to_dict()` / `from_dict()` 实现完整上下文序列化，支持会话恢复。反序列化时将 `resume_data` 与空模板合并，以处理 Schema 演进导致的字段增减。

## 4. 持久化层 — 存储后端

### 4.1 统一抽象接口

文件：`memory/memory_manager.py`

```python
class BaseMemory(ABC):
    async def store(content, metadata) -> str      # 存储
    async def search(query: MemoryQuery) -> List   # 搜索
    async def delete(memory_id) -> bool            # 删除
    async def clear()                              # 清空
    async def get(memory_id) -> Optional           # 获取
    async def update(memory_id, content, metadata) -> bool  # 更新（默认实现：删后重建）
```

### 4.2 结构化存储 — JSON 后端

文件：`memory/structured_memory.py :: JSONStructuredMemory`

| 特性 | 说明 |
|------|------|
| 存储方式 | `memories.json` 文件，全量加载到内存 Dict |
| 备份策略 | 写入前自动备份为 `.json.backup` |
| 搜索方式 | substring 匹配（`query.text in content`） |
| 元数据过滤 | Python 侧精准匹配 |
| 排序 | 按 timestamp 降序 |
| 适用场景 | 开发调试、单用户、数据量小的场景 |

### 4.3 结构化存储 — SQLite 后端

文件：`memory/structured_memory.py :: SQLiteStructuredMemory`

| 特性 | 说明 |
|------|------|
| 表结构 | `memories(id, content, metadata, timestamp, created_at)` |
| 索引 | `idx_memories_timestamp` |
| 文本搜索 | SQL `LIKE '%keyword%'` |
| 元数据过滤 | Python 侧反序列化 JSON 后匹配 |
| 连接管理 | 每次操作创建独立连接，`row_factory = sqlite3.Row` |
| 适用场景 | 多用户、生产环境、对持久性要求高的场景 |

### 4.4 向量存储 — ChromaDB

文件：`memory/vector_memory.py :: ChromaVectorMemory`

| 特性 | 说明 |
|------|------|
| 嵌入模型 | `all-MiniLM-L6-v2` (sentence-transformers) |
| 后端引擎 | duckdb+parquet |
| 持久化目录 | `./data/chromadb/` |
| 相似度计算 | cosine distance → `1.0 - distance` |
| 惰性初始化 | 首次操作时加载模型和集合 |
| 适用场景 | 语义搜索、相似对话检索、基于内容的推荐 |

### 4.5 MemoryManager — 混合记忆协调器

文件：`memory/memory_manager.py :: MemoryManager`

同时持有 `vector_memory` 和 `structured_memory` 两个后端，提供统一的高级接口：

| 方法 | 行为 |
|------|------|
| `store_conversation(user_id, conversation)` | 对话文本存向量 + 结构化元数据存 SQLite/JSON |
| `store_user_profile(user_id, profile)` | 画像 JSON 存结构化 + 摘要文本存向量 |
| `store_skill(user_id, skill_data)` | 技能数据存结构化 + 描述文本存向量 |
| `search_conversations(user_id, query_text)` | 有文本→向量语义搜索，无文本→最近对话 |
| `get_user_profile(user_id)` | 仅查询结构化存储 |
| `get_user_skills(user_id)` | 批量查询技能数据 |
| `health_check()` | 两端写入/删除健康检测 |

### 4.6 ResumeStore — 简历数据持久化

文件：`memory/resume_store.py`

专用于简历数据的存取，基于结构化存储的一个记录对应一个用户的设计：

```python
class ResumeStore:
    async def save(user_id, resume_data)       # upsert：查找旧记录→更新或创建
    async def load(user_id) -> dict | None     # 加载并 merge schema 模板
    async def delete(user_id) -> bool          # 删除用户记录
    async def exists(user_id) -> bool          # 检查是否存在
```

每个用户有唯一标识：metadata `{"user_id": <id>, "type": "resume_data"}`。

## 5. 提取层 — 被动信息提取

### 5.1 设计哲学

- **被动提取**：用户提及才提取，不主动追问
- **增量输出**：每次只输出变更部分（delta），不重复已有数据
- **忠实原文**：尽量保留用户原始表述，不改写

### 5.2 Delta 提取流程

```
用户消息 + 已有简历数据
        │
        ▼
┌─────────────────────────────────────┐
│  LLM 分析                            │
│  system_prompt: 动态构建自 schema     │
│  user_input: 已有数据 + 最新消息      │
│  temperature: 0.1 (一致性优先)        │
│  max_tokens: 2048                    │
└──────────┬──────────────────────────┘
           │ delta（JSON 对象）
           ▼
┌─────────────────────────────────────┐
│  merge_extracted_fields(existing,   │
│     delta) → None (in-place)       │
│   根据字段类型路由到 4 种合并策略     │
└─────────────────────────────────────┘
```

### 5.3 四种合并策略

#### 标量字段（SIMPLE_OVERWRITE_KEYS）
12 个字段：`target_position`, `target_industry`, `target_location`, `name`, `gender`, `phone`, `email`, `photo`, `graduation_date`, `availability`, `personal_summary`

策略：直接覆盖已有值。

#### 字典字段（DICT_MERGE_KEYS）
3 个字段：`hard_skills`, `language_skills`, `portfolio_links`

策略：update 合并，新 key 增加，已有 key 覆盖。

#### 列表字段（LIST_APPEND_KEYS）
3 个字段：`soft_skills`, `certificates`, `other_experiences`

策略：遍历新元素，去重追加。

#### 重复组字段（REPEATING_FIELD_KEYS）
3 个字段：`education_list`, `work_experience_list`, `project_experience_list`

支持两种操作：
```json
// 添加新条目
{"education_list": [{"_op": "add", "school": "北京大学", "major": "软件工程"}]}

// 更新已有条目（按 _match 匹配）
{"education_list": [{"_op": "update", "_match": {"school": "北京大学"}, "gpa": "3.8/4.0"}]}
```

### 5.4 LLM 提取提示词

系统提示词在模块加载时**动态构建**，自动引用 `resume_schema.py` 的完整字段定义。当 Schema 增加字段时，提取提示词自动同步，无需手动维护。

### 5.5 正则辅助提取

BrainAgent 的 `_extract_user_profile()` 中包含轻量级正则快速通道，用于提取高频简单信息：

| 模式 | 提取目标 |
|------|---------|
| `大[一二三四]` / `研[一二三]` | 年级 |
| `的(.{2,6})学生` / `(.{2,6})专业` | 专业 |
| `[\u4e00-\u9fff]{2,8}(?:大学\|学院)` | 学校 |
| `(?:学习\|学\|提升\|掌握).{2,20}` | 技能关注点 |

正则提取为**同步快速通道**，LLM 提取为**异步完整通道**，两者互补。

## 6. 情感追踪系统

### 6.1 情绪记录

```python
ctx.record_mood(mood="happy" | "neutral" | "stressed" | "anxious" | "discouraged" | "confident",
                trigger="interview rejected")
```

### 6.2 逐轮情感分析

BrainAgent 每轮对话后调用 `record_emotion_analysis()`，记录结构化分析结果：

```python
{
    "emotions": ["焦虑", "期待"],
    "overall_state": "negative" | "neutral" | "positive" | "crisis",
    "support_intensity": "none" | "mild" | "strong" | "crisis",
    "demand_type": "work_guidance" | "emotion_support" | "domain_question" | ...,
    "confidence": 0.0 ~ 1.0
}
```

### 6.3 累积状态评估

`get_accumulated_emotion_assessment(window=5)` 综合判断：

- `negative_ratio` — 窗口内负面情绪比例
- `consecutive_negative` — 连续负面轮次
- `should_defer_work` — 是否应将工作类请求路由到情绪 Agent
- `reason` — 中文可读的原因说明

**判断逻辑**：连续 2+ 轮负面 || 负面占比 > 60% || mood_trend 认为需干预 → 延迟工作

### 6.4 情绪路由

BrainAgent 收到用户消息后：
1. 分析用户需求（工作指导 / 情绪支持 / 其他）
2. 如果需求为工作指导 → 检查 `should_defer_work`
3. 如需延迟 → 路由到 `EmotionAgent` 而非 `WorkAgent`
4. 如果需求为情绪支持 → 直接路由到 `EmotionAgent`

### 7.1 用户消息处理流程

```

    │
    ▼
```

## 9. 关键设计决策

### 9.1 为什么用 Schema + Data 双层结构？

- **Schema 驱动开发**：字段定义、提取提示、校验规则集中在 `resume_schema.py`，一处修改全局生效
- **Schema 演进**：新增字段只需加一个 `ResumeFieldDef`，template merge 自动兼容旧数据
- **LLM 提示自同步**：提取提示词动态从 Schema 构建，无需手动维护两份定义

### 9.2 为什么用 Delta 增量而非全量更新？

- **节省 Token**：每次只传递变更字段，LLM 输出小且快
- **防覆盖**：多轮对话中，后一轮不会意外抹除前一轮已提取的信息
- **可追溯**：`_op: add` / `_op: update` 可追溯每条数据的来源和变更

### 9.3 为什么用混合记忆架构？

- **向量记忆**：适合「找到之前聊过的相关内容」的语义检索
- **结构化记忆**：适合「用户简历数据」的精确存取
- **互补不足**：向量搜索不保证精确匹配，结构化搜索不支持模糊语义

### 9.4 为什么正则 + LLM 双通道提取？

- **正则通道**：零延迟、零成本，覆盖高频确定性模式（年级、专业、学校）
- **LLM 通道**：识别复杂、开放式的简历信息（技能水平、项目描述、工作职责）
- **互补关系**：正则处理不了的才交由 LLM，最大化效率
