# OpenCareer 技术决策与前期规划文档

**文档目的**：记录系统开发过程中的关键技术决策，明确前期不实现的功能，方便后期查验补充。

**更新日期**：2026-04-19
**讨论方式**：通过问答选择确定技术方案

---

## 一、已确认的技术决策

### 1. 对话记忆与上下文管理
- **上下文窗口处理**：采用向量检索方案
  - 使用向量数据库存储历史对话
  - 检索最相关的对话片段组合
  - 避免固定窗口截断信息丢失

- **数据组织方式**：混合模式
  - 对话历史 → 向量检索存储
  - 结构化数据（个人信息、学习计划进度） → JSON文件 + SQLite数据库
  - 平衡检索效率与结构化查询需求

- **上下文共享机制**：共享内存区域
  - 设立共享的上下文存储区
  - 所有智能体都可读写（需注意并发控制）
  - 便于智能体间信息交换

### 2. 多智能体协作通信机制
- **大脑与代理通信**：直接函数调用
  - 大脑直接调用代理的方法（支持异步调用）
  - 简单直接，减少中间件复杂度
  - 适合前期开发验证

- **协同工作模式**：事件协作
  - 代理间通过事件机制自动协作
  - 大脑仅作初始触发
  - 支持灵活的代理间交互

- **日志信息获取**：定期扫描共享内存
  - 日志代理定期扫描共享上下文存储区
  - 提取新增对话内容进行结构化
  - 避免频繁事件订阅开销

### 3. 错误处理与容错恢复
- **代理故障处理**：自动重试
  - 在限制次数内自动重试失败操作
  - 仍失败则返回降级响应
  - 提高系统韧性

- **大脑故障处理**：前期无需特殊处理
  - 假设大脑稳定运行
  - 故障时人工干预重启
  - 后期可升级为进程监控重启

- **外部API故障**：返回友好错误
  - 向用户返回清晰的错误信息
  - 建议稍后重试
  - 不尝试复杂降级策略

### 4. 配置管理与环境隔离
- **敏感配置存储**：环境变量
  - API密钥等敏感信息通过环境变量传递
  - 适合容器化部署
  - 避免配置文件泄露风险

- **环境隔离**：后期考虑
  - 前期单一环境配置
  - 需要部署到生产环境时再添加多环境支持
  - 保持前期开发简单性

### 5. 监控、日志与可观测性
- **日志记录策略**：结构化日志
  - 输出JSON格式的结构化日志
  - 便于后续分析和处理
  - 支持日志聚合和分析工具

- **监控指标**：基础健康指标 + 性能指标
  - API可用性、服务运行状态
  - 响应时间、错误率、请求量
  - 不监控资源指标（CPU、内存等）

### 6. 智能体实现架构
- **基类设计**：最小功能集 + 扩展式架构
  - 前期采用最小功能集（提示词加载、消息处理）
  - 设计支持插件化扩展的架构
  - 预留功能模块动态添加接口

- **通信机制**：直接函数调用 + 回调
  - 大脑直接调用代理方法，支持异步调用
  - 通过回调函数返回处理结果
  - 简单直接，减少中间件复杂度

- **状态管理**：混合状态管理模式
  - 实例状态：智能体连接、配置等实例级状态
  - 会话状态：处理上下文等会话级状态，由状态管理器分离管理
  - 平衡实例资源复用与会话数据隔离

- **实例化策略**：单例模式
  - 每个智能体类型只有一个实例
  - 通过锁机制保证线程安全
  - 适合前期低并发场景，简化资源管理

### 7. SKILLs与MCP实现
- **SKILLs交互模式**：混合调用模式
  - 核心功能SKILLs：智能体直接函数调用，保证性能和简单性
  - 扩展功能SKILLs：通过MCP Server调用，保证可扩展性和热插拔
  - 平衡核心性能与扩展灵活性

- **SKILLs开发规范**：严格统一接口
  - 要求所有SKILLs遵循统一的接口规范
  - 确保输入输出格式、错误处理、配置方式的一致性
  - 支持SKILLs的可替换性和组合使用

- **MCP Server实现**：动态目录扫描加载
  - MCP Server自动扫描skills目录加载可用SKILLs
  - 支持SKILLs的热插拔和动态更新
  - 提供SKILLs注册、发现和调用管理功能

- **SKILLs目录结构**：标准模块化结构
  - 遵循SKILL.md + 资源文件的标准化结构
  - 支持scripts/、references/、assets/等标准子目录
  - 确保SKILLs的独立性和可移植性

### 8. 其他决策
- **用户身份管理**：前期不重要
  - 前期开发阶段不实现用户认证
  - 后期根据需求再添加

- **安全隐私控制**：前期不实现
  - 数据加密存储 → 后期实现
  - 访问控制 → 后期实现

- **并发控制**：前期无需控制
  - 假设串行访问或竞态条件可接受
  - 后期根据并发需求再添加锁机制

- **测试策略**：前期暂无测试
  - 专注于功能实现
  - 测试在后期功能稳定后补充

## 三、技术栈具体选择

### 已确定组件
1. **向量数据库**：**ChromaDB**（客户端-服务器模式）
   - 存储对话历史，支持向量检索
   - 客户端-服务器架构，可独立运行ChromaDB服务
   - 提供语义搜索和相似度匹配功能

2. **事件与消息队列**：**dramatiq + Redis**
   - dramatiq：功能丰富的Python任务队列库，支持重试、延迟等特性
   - Redis：作为dramatiq的消息代理（broker），提供持久化消息存储
   - 用于智能体间的事件协作和异步任务处理

3. **日志系统**：**python-json-logger**
   - 简单的JSON日志格式化器
   - 输出结构化日志，便于后续分析和处理
   - 与Python标准logging库集成

4. **依赖管理**：**Poetry**（通过pyproject.toml）
   - 现代Python依赖管理工具
   - 支持虚拟环境管理、依赖分组
   - 便于开发、测试、生产环境依赖隔离

5. **配置管理**：**环境变量直接读取**
   - 通过os.environ直接读取环境变量
   - 适合容器化部署
   - 敏感信息（API密钥）通过环境变量传递

6. **结构化数据存储**
   - SQLite：轻量级关系数据库，适合单机部署
   - JSON文件：简单配置和数据结构存储

7. **异步框架**：Python asyncio
   - 内置支持，无需额外依赖
   - 配合ThreadPoolExecutor处理阻塞操作

8. **数据验证**：前期使用普通字典，后期迁移到**Pydantic**
   - 前期开发保持简单，使用字典传递数据
   - 后期添加Pydantic进行类型安全和数据验证

### 已解决的前期决策
1. **ChromaDB存储模式**：客户端-服务器模式（独立运行ChromaDB服务）
2. **dramatiq消息代理**：Redis（生产级持久化存储）
3. **事件协作实现**：dramatiq作为事件总线，支持代理间异步协作

## 六、风险与假设

### 技术风险
1. **向量检索性能**：对话历史量增长后检索效率
2. **共享内存并发**：多代理同时访问可能的数据竞争
3. **异步编程复杂度**：错误处理和调试难度
4. **模型API稳定性**：依赖外部服务的可用性

### 项目假设
1. **低并发场景**：前期支持少量并发用户
2. **单机部署**：前期不考虑分布式部署
3. **手动运维**：前期故障需要人工干预
4. **功能优先级**：核心求职功能优先于系统管理功能
